# DESIGN — new interface workflow

## Trigger

A new site, landing page, application screen, or component is requested. If the user asks to redesign an existing interface, use \`redesign.md\` instead.

## Procedure

1. **Scope** — restate the exact requested deliverable and known non-goals. Check project code/assets if relevant and available.
2. **Inputs** — list confirmed content, intended task, actions, device requirements, approved visual direction, technical restrictions. Ask only for missing facts that will materially change a design decision.
3. **UX skeleton** — identify the main user action, content priority, route or hierarchy, states and error handling. Do not create new features.
4. **Choose direction if open** — apply \`decision-making.md\` and \`../references/style-selection.md\`. For unapproved hypotheses, submit options and stop before locking the direction.
5. **Visual system** — select or extend fonts, semantic colors, spacing, grid, image treatment, radii/borders, interactions. Prefer existing design-system values.
6. **Detail** — specify screen regions and exact or responsive rules; include dense/empty/loading/error/focus/disabled states if relevant; cover long text and narrow screens.
7. **Deliver** — output the requested artifact: proposal, blueprint, component spec, or code (only when explicitly authorized). Use \`../templates/design-handoff.md\` when handing to engineering.
8. **Boundary** — in-process visual checks may inform design, but do not perform a separate final visual QA or claim acceptance.

## Stop points

Ask approval when a major new visual direction, UX structure, new behavior, or brand-defining asset is not authorized. Don't ask for confirmation of every ordinary spacing or token choice when the rules already cover them.
